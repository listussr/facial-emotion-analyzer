# `service_health` — живость и готовность сервисов

Модель распознавания эмоций загружается от нескольких секунд до полутора минут. Анализ, запущенный
раньше, теряет модальность: пока сервис голоса загружает WavLM, он не читает звук, а потом отбрасывает
его как устаревший. Поэтому каждый сервис сообщает, загружает ли он модели или уже работает. Веб-сервер не
запускает сессию, пока нужные ей сервисы не готовы, и показывает их состояние в интерфейсе.

```
src/service_health/
├── heartbeat.py   ServiceBeat, Heartbeat, heartbeat_from_env
└── store.py       ServiceHealthStore, summarize, not_ready_reasons
```

---

## Сигнал (`Heartbeat`)

Каждый процесс создаёт `heartbeat_from_env("<сервис>")` в самом начале, а после загрузки моделей вызывает
`ready(...)`. Фоновый поток раз в `HEARTBEAT_INTERVAL_S` (5 с) публикует `ServiceBeat` в compacted-топик
`service-health` с ключом `сервис@хост-pid`.

| Поле | Смысл |
|---|---|
| `service`, `instance`, `host` | имя сервиса, экземпляр, хост |
| `state` | `starting` — загружает модели, `ready` — обрабатывает данные |
| `started_at`, `updated_at` | время запуска и последнего сигнала |
| `info` | что загружено: модель, детектор, VAD, метод слияния, адрес узла приёма |

- **Файл готовности.** В состоянии `ready` сигнал каждый раз обновляет `HEALTH_FILE` (`/tmp/affectra-ready`
  в Docker). Healthcheck контейнера проверяет, что файлу не больше 30 с, поэтому `docker ps` показывает
  `healthy` только после загрузки моделей.
- **Остановка.** При нормальной остановке запись удаляется tombstone. Если процесс упал, его запись устаревает.
- **Ошибки Kafka** сервис не роняют: сигнал просто пропускается.

| Сервис | Готов после |
|---|---|
| `ingest` | создания сервиса приёма и чтения `session-status` |
| `consumer` | загрузки детектора, трекера и модели лица |
| `audio-consumer` | загрузки модели голоса и Silero VAD |
| `fusion` | создания сервиса слияния |
| `visualizer`, `archiver` | создания сервиса |

## Готовность (`ServiceHealthStore`, `summarize`, `not_ready_reasons`)

Веб-сервер держит копию топика. `summarize` считает экземпляры каждого сервиса: `ready`, `starting` и `stale`
(сигнал старше 20 с). Сервис готов, если у него есть хотя бы один готовый экземпляр.

| Модальность сессии | Нужны |
|---|---|
| `video` | `ingest`, `consumer`, `fusion` |
| `audio` | `ingest`, `audio-consumer`, `fusion` |

`not_ready_reasons(health, modalities)` возвращает причины по-русски: «анализ голоса: сервис загружает модели»
или «…: сервис не запущен». `SessionManager.check_ready` вызывается до публикации конфига и команды. Если
причины есть, он бросает `StartError`, и API возвращает 400 с этим текстом. Проверку можно выключить
(`AFFECTRA_REQUIRE_READY=false`). Пока веб-сервер не дочитал топик, проверка не выполняется.

`GET /api/health` дополнительно возвращает:

- `services` — по каждому сервису его название и число экземпляров `ready` / `starting` / `stale`;
- `ready_for` — можно ли запускать видео и голос;
- `not_ready` — общий список причин.

Шапка интерфейса показывает «модели загружаются…» с причинами во всплывающей подсказке. Пока сервисы не
готовы, опрос идёт раз в 3 с.

## Проверка

На полном стеке сразу после `docker compose up` `/api/health` показал, что лицо и голос загружают модели, и
запуск сессии был отклонён. Через несколько секунд все сервисы стали `ready` и `healthy`. Первая сессия на
ролике с речью получила голос во всех 13 окнах речи.

При перезапуске `audio-consumer` сессия с голосом отклонялась, а сессия только с видео запускалась. Через
4 с голос снова стал доступен.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TOPIC_SERVICE_HEALTH` / `AFFECTRA_TOPIC_SERVICE_HEALTH` | `service-health` | топик сигналов |
| `HEARTBEAT_INTERVAL_S` | `5` | период сигнала |
| `HEALTH_FILE` | не задан (в Docker `/tmp/affectra-ready`) | файл для healthcheck контейнера |
| `AFFECTRA_REQUIRE_READY` | `true` | не запускать сессию до готовности нужных сервисов |
