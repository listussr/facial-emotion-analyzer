# Развёртывание

Сервисы Affectra общаются только через Kafka, S3 и PostgreSQL, поэтому одну и ту же сборку можно запустить на
одной машине или разнести по нескольким. Режимы ниже идут от простого к распределённому, код в них один и тот же.

| Режим | Файлы | Когда |
|---|---|---|
| Одна машина | `docker-compose.yml` | разработка, демонстрация |
| Kafka из трёх узлов | `+ docker-compose.kafka-cluster.yml` | проверка отказоустойчивости брокеров на одной машине |
| Два узла приёма | `+ docker-compose.multi-ingest.yml` | проверка распределения сессий и пересылки камеры браузера |
| Несколько машин | `deploy/docker-stack.yml` (Docker Swarm) | распределённая установка |

Файлы compose можно сочетать. При переходе между режимами сначала выполните `docker compose down`: топики
создаются заново с нужными партициями и репликацией.

---

## 1. Одна машина

```bash
docker compose up -d --build
```

Kafka работает в режиме KRaft (брокер и контроллер в одном процессе, без ZooKeeper), у топиков одна реплика.
Подробности — в [README](../README.md#1-быстрый-старт-docker).

## 2. Kafka из трёх узлов

```bash
docker compose -f docker-compose.yml -f docker-compose.kafka-cluster.yml up -d --build
```

- Три узла `kafka`, `kafka-2`, `kafka-3`. Каждый совмещает брокер и контроллер, кворум контроллеров — 2 из 3.
- Топики создаются с `replication.factor=3` и `min.insync.replicas=2`.
- Сервисы получают адреса всех трёх брокеров.

Проверено остановкой брокера-лидера. Лидерство перешло на другой узел, а запись статусов с `acks=all` и их
чтение продолжились. Вернувшийся брокер догнал реплики. Каждый брокер занимает около 350 МБ памяти.

## 3. Два узла приёма

```bash
docker compose -f docker-compose.yml -f docker-compose.multi-ingest.yml up -d
```

- **Распределение команд.** Узлы `ingest` и `ingest-2` делят команды сессий по партициям `session-commands`. Партиций по умолчанию 2: их должно быть не меньше, чем узлов.
- **Балансировка.** nginx раздаёт WebSocket камеры браузера по обоим узлам.
- **Пересылка.** Узел, у которого нет сессии, пересылает медиа её владельцу (см. [ingest.md](modules/ingest.md#несколько-узлов-приёма)).

## 4. Несколько машин: Docker Swarm

### Роли узлов

| Метка узла | Сервисы | Требования |
|---|---|---|
| `affectra.kafka=1`, `=2`, `=3` | `kafka-1`, `kafka-2`, `kafka-3` | по одному брокеру на машину, диск под данные Kafka |
| `affectra.core=true` | `postgres`, `s3`, `webapp`, `frontend` (порт 8080) | диск под БД и записи |
| `affectra.ingest=true` | `ingest` (2 экземпляра) | сеть до камер и до Kafka |
| `affectra.compute=true` | `consumer`, `audio-consumer`, `fusion`, `visualizer`, `archiver` | CPU, модели в `/opt/affectra/models/crema` |

Одной машине можно дать несколько меток. Минимальная установка с отказоустойчивой Kafka — три машины: на
каждой по брокеру, а остальные роли распределены между ними.

### Подготовка

1. **Синхронизация времени.** Все машины синхронизируют часы по NTP, например через chrony:
   `apt install chrony`, затем `chronyc tracking` (смещение должно быть в пределах единиц миллисекунд). Почему
   это важно — в разделе 5.
2. **Порты Swarm** между машинами: 2377/tcp, 7946/tcp+udp, 4789/udp. Снаружи нужен только порт 8080.
3. **Swarm и метки:**

   ```bash
   docker swarm init --advertise-addr <IP менеджера>
   docker swarm join --token <токен> <IP менеджера>:2377
   docker node update --label-add affectra.kafka=1 --label-add affectra.core=true node-a
   docker node update --label-add affectra.kafka=2 --label-add affectra.ingest=true node-b
   docker node update --label-add affectra.kafka=3 --label-add affectra.compute=true node-c
   ```

4. **Реестр образов.** Swarm не собирает образы: узлы берут их из реестра.

   ```bash
   docker run -d -p 5000:5000 --restart=always --name registry registry:2
   REGISTRY=<IP менеджера>:5000 deploy/push-images.sh
   ```

   Для реестра без TLS добавьте его в `insecure-registries` в настройках Docker на каждом узле.
5. **Модели** CREMA-D распакуйте на узлах с меткой `compute` и на узле `core` в `/opt/affectra/models/crema`.
   Другой путь задаётся переменной `MODELS_DIR`.

### Запуск

`docker stack deploy` не читает `.env`, поэтому переменные экспортируются в окружение:

```bash
set -a; . ./.env; set +a
REGISTRY=<IP менеджера>:5000 docker stack deploy -c deploy/docker-stack.yml affectra
docker service ls
```

Swarm не ждёт зависимостей. Поэтому `topics-init` перезапускается, пока все три брокера не примут создание
топиков, а остальные сервисы переподключаются к Kafka сами. Через 1–2 минуты все сервисы в состоянии
`1/1` (`ingest` — `2/2`), а `topics-init` завершён.

### Особенности стека

- **Брокеры** работают с `endpoint_mode: dnsrr`. Клиент держит долгое соединение с конкретным брокером, а
  виртуальный IP Swarm закрывает простаивающие соединения.
- **Узлы приёма** работают за виртуальным IP сервиса `ingest`. Swarm распределяет WebSocket браузера по ним,
  а пересылка доводит медиа до владельца сессии. Адрес узла для пересылки — IP контейнера в overlay-сети.
- **Партиции.** По умолчанию у топиков 4 партиции (`TOPIC_PARTITIONS`), поэтому `consumer`, `audio-consumer`
  и `ingest` можно масштабировать до 4 экземпляров: `CONSUMER_REPLICAS`, `AUDIO_CONSUMER_REPLICAS`,
  `INGEST_REPLICAS` или `docker service scale`. Сессия целиком обрабатывается одним экземпляром: ключ всех
  сообщений — `camera_id`, а партиции одинаковых номеров достаются одному экземпляру.
- **Healthcheck.** Сервисы с моделями становятся `healthy` только после загрузки моделей (файл готовности,
  см. [service_health.md](modules/service_health.md)). При обновлении стека Swarm ждёт этого, прежде чем
  считать задачу запущенной.
- **Одиночные сервисы.** PostgreSQL, S3, веб-сервер, слияние и архиватор работают в одном экземпляре. При
  падении Swarm перезапускает их, данные остаются в томах узла `core`.

### Проверка

Стек проверен на Swarm из одного узла: все метки на одной машине, сервисы обработки не запускались.

- Три брокера собрали кворум, `topics-init` создал 10 топиков с 4 партициями и 3 репликами.
- Оба узла приёма запустились.
- Веб-сервер через фронтенд видит Kafka.
- Шесть сессий камеры браузера разошлись по двум узлам приёма. WebSocket пересылался в обе стороны по
  overlay-сети без потерь кадров, все сессии корректно завершились.

## 5. Время на узлах

Время захвата кадра ставит узел приёма, а возраст кадра считают сервисы обработки на других машинах. Кадры
старше `MAX_FRAME_AGE_MS` (1 с), чанки звука старше `MAX_CHUNK_AGE_MS` (2 с) и кадры аналитики в слиянии
старше 2 с отбрасываются. Поэтому при расхождении часов больше этих порогов обработка может выбросить все кадры.

Сами сервисы это обнаруживают (`StalenessFilter`) и пишут предупреждение не чаще раза в минуту:

- кадр пришёл «из будущего» больше чем на 0,5 с — часы источника спешат;
- 100 кадров подряд устарели — обработка отстаёт или часы источника отстают.

Оба сообщения в логе заканчиваются пометкой `(NTP)`. Внутри Docker контейнеры используют часы хоста, поэтому
синхронизировать нужно сами машины.

## 6. Ограничения

- PostgreSQL и S3 не реплицируются: это одиночные сервисы на узле `core`, резервные копии их томов нужно
  делать отдельно. Для отказоустойчивости хранения нужны репликация PostgreSQL и SeaweedFS с несколькими
  volume-серверами.
- Веб-сервер работает в одном экземпляре: события и живой показ он держит в памяти процесса.
- TLS между узлами не настроен, но overlay-сеть можно шифровать (`driver_opts: encrypted: "true"`). Фронтенд
  слушает HTTPS на 8443 с самоподписанным сертификатом для адресов из `TLS_HOSTS`, или со своим
  сертификатом в томе `frontend_certs` (см. README).
